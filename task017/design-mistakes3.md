1. Первый пример по дипломному проекту. 
 
Тут я вспомнил одно из заданий дипломного проекта по выносу работы с базой из сервисов непосредственно в контроллеры - ряд сервисов, представлявших собой обычные прокси к репозиторию были полностью удалены. 
И вот тогда еще была попытка разделения сервисов на IOService (и использование его в контроллере) и сервис непосредственно для логики домена.
Подумал, что как вариант нелокального рефакторинга это будет в принципе хороший пример. В рамках данной системы учета автопарка получается что для ряда сервисов можно разделить обработку ввода-вывода и непосредственно на работу с логикой домена (правила, запись в репозиторий и т.п.). 
Сейчас все действия по переводу/преобразованию форматов входных и выходных данных, взаимодействие с репозиторием, проверка правил находится в одном сервисе. Но плюс к этому, часть действий с системой (импорт, отправка событий в кафку, DashboardService) не учитывает или не использует данные сервисы для сущностей приложения.
После рефакторинга должно получиться (на примере сервиса для предприятий) что-то вроде такого варианта:

EnterpriseIOService вызывается из контроллера и отвечает за преобразование данных при получении параметров предприятия (для редактирования например) или наоборот, для показа информации по предприятию - разбор и обработка JSON.
DashboardService избавляется от обработки JSON и вызывает только методы из EnterpriseIOService (ранее разбор дублировался в обоих сервисах) - в общем это доп пример, когда вроде бы при широком взгляде на систему всплывают незамеченные ранее частные случаи неправильной организации кода.
Контроллер предприятия взаимодействует только с EnterpriseIOService.

EnterpriseService становится единственным ответственным за проверку правил и за запись. Здесь проверка на принадлежность предприятия менеджеру, ивенты для veholder-stats публикуются здесь, после сохранения (создание/изменение/удаление). На самом деле сейчас это публикует контроллер (метод PUT), т.е. импорт и админка меняют предприятие без события.

После рефакторинга все (админка, контроллер, импорт) манипуляции с предприятием проходят через единые точки в EnterpriseService (create, update, deleteEnterprise). Разбор JSON и вообще все, что относится только к IO вынесено в EnterpriseIOService.
Данные изменения хорошо ложатся на несколько сервисов (VehicleService, DriverService, VehicleTrackService), но есть и сервисы системы, для которых такой подход не подойдет. 

2. По рабочему проекту.

Тут я скорее пофантазирую, потому что вряд ли смогу это предложить как реальное рабочее предложение тимлиду, по крайней мере сейчас.
У нас главный управляющий актор (ManagerActor) мне кажется разросся уже до неприличных размеров - это уже под 5000 строк, больше 40 веток match и соответственно почти 50 методов on... (это которые типа onFindObjectResponse).
В одном акторе сейчас чтение пачки, поиск, вставка RunData, сценарий (скрипт), ожидание callback, статусы операции и заявки, пауза/останов.
В текущем решении уже есть вынос ряда процессов из этого главного актора, например CheckManagerActor ответственный за проверку сущностей. 
Идея в том, чтобы не механически разделить код на отдельные классы, соответствующие сообщениям. А так как данные сообщения можно сгруппировать по процессам, то вынести сами эти процессы с группами соответствующих им сообщений.
В самом ManagerActor уже есть такое деление по жизненному циклу запуска - RunInternalState: сбор RunData, внешняя проверка, выполнение операции, финальная статистика, пауза, останов, конец. И по этому ЖЦ в processRun через switch идет определение следующих шагов обработки.  
Но фактически сейчас чтобы понять весь путь запуска (или, не дай бог, вставить новый шаг в ЖЦ или внутрь статуса) надо смотреть не только на собственно processRun, а еще и найти всю цепочку методов on... обрабатывающих дополнительные внутренние переходы внутри статуса ЖЦ.

Например, для 
```java
switch (runInfo.getInternalState()) {
    case BUILDING_RUN_DATA:
        processBuildingRunData(runInfo);
        break;
```
- onReadNewLoadDataResponse - страница с LoadData пришла. Пустая страница ставит ЖЦ-статус WAITING_OTHER_RUN_DATA (вызывает processRun). Непустая на каждую строку шлёт FindObjectRequestMessage.
- onFindObjectResponse - поиск что-то вернул. Бизнес-ошибка или исчерпанные попытки дают MarkErrorLoadDateRequestMessage. Успех с клиентом/абонентом готовит RunData и шлёт RunDataInsertRequestMessage. Пустой субъект тоже помечает строку ошибкой.
- onRunDataInsertResponse - сообщение о результатах вставки рандаты. Успех уменьшает счётчик ожидания и зовёт processRun. Бизнес-ошибка отменяет запуск. Прочая ошибка планирует ту же вставку ещё раз.
- processBuildingRunData - решает, читать ли следующую страницу, только когда счётчик ожидания дошёл до нуля.

Если же сгруппировать все действия по статусу ЖЦ, то можно получить единый вход такого "участка", который принимает не сообщения, а конкретный факт, вне зависимости от сообщения, которым он вызван.
т.е.
- пришла страница строк - выходом будет команда поиска на каждую строку
- объект найден - выход: команда вставки RunData 
- объекта нет или ошибка BusinessException - команда для пометки такой строки 
- ошибка инфраструктуры и попытки ещё есть - выход: команда на повтор поиска
- вставка прошла - выход: уменьшаем ожидание и, если ждать больше нечего, сменить положение 
- вставка упала с BusinessException - выход: отменяем запуск.

Фактически ManagerActor превращается в переводчика с "языка" сообщений на "язык" фактов для статуса ЖЦ.
Если разрезать ManagerActor по сообщениям (точнее по match), то получится около сорока классов, и, например, участок по сбору RunData (BUILDING_RUN_DATA) все-равно будет обрабатываться тремя классами из них, ну и плюс лежать в processRun. 
Объём файла уменьшится, но ход обработки останется разрезанным по классам.

Группировка же по статусу ЖЦ идёт от processRun, который уже основан на RunInternalState, и позволяет иметь новые классы по числу участков (ну статусов) ЖЦ запуска, а не по числу типов сообщений.
