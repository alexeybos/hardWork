Постарался для всех вариантов найти примеры в нашем коде:

#### Для "2.1. Класс слишком большой (нарушение SRP)" пример нашелся прямо по комментарию в классе
```java
// Реестр задач на исполнение. Он же кеш, он же очередь. По каждому слоту свой.
```
В классе TaskDispatcher почти 1300 строк, он имеет (это как минимум) пять разных причин для изменения (собственно критерий SRP): 
- политика распределения задач, 
- обработка/матчинг callback'ов, 
- запрос обновлений из БД, 
- процедура recovery задач, 
- процедура для graceful stop. 

Соответственно при изменении любой из них получаем правку одного и того же файла на 1300 строк, со всеми причитающимися рисками.
Отдельно наверное стоит упомянуть и проблему отказоустойчивости. Проблемы в одном из, по сути отдельных, жизненных циклов, рестартуют актор целиком, "убив" реестры, очереди воркеров и остальное.

Исправление видится (высокоуровнево) в следующем: актор должен только принимать сообщения и делегировать. Остальное должно быть вынесено в отдельные классы, например как WorkerMatcher для логики назначения задач воркерам, CallbackMatcher для работы с коллбэками и т.д.  

По второй части вопроса ("в программе создаётся слишком много его инстансов, почему это может быть плохо"): слишком частое создание экземпляров какого-нибудь класса может указывать на то, что он делает слишком много, т.е. как раз признак нарушения SRP.

#### 2.2 Класс слишком маленький или делает слишком мало
Источником проблем для этого пункта может быть создание класса "на будущее", когда при проектировании предполагалась какая-нибудь сущность/поведение системы, но в реальности это не появилось или "отменилось" уже на этапе реализации.

Подмена классами-маркерами обычного enum. Тут у нас в коде есть пример 9 классов для последующей проверки instanseof:
```java
@ToString
@AllArgsConstructor
public class ProxyContextCancelBulkRequest {

}
@ToString
@AllArgsConstructor
public class ProxyContextPauseBulkRequest {

}
// и т.п.
```

Ну и слишком механическое следование SRP - когда класс дробят буквально до одного метода. Получается класс, который нельзя понять и использовать отдельно т.к. он только часть чужого алгоритма, т.е. у него нет самостоятельной ответственности.
Кстати, проблема появления таких классов может возникнуть как раз из рефакторинга больших классов типа того, что приведен в примере в самом начале (TaskDispatcher). Когда новые сущности создаются, но вся логика остается в основном классе.

#### 2.3. В классе есть метод, который выглядит более подходящим для другого класса. 
В рабочем коде нашел вот такой ужас....
```java
public class TaskExecutor extends AbstractActorWithTimers {
    //.....
    // осознанно копировано из ScenarioExecutor.
    private Pair<OapiWrapper, OapiWrapper> buildOapiWrapperForData(List<RunDataExecutionRequest> requestList, OapiWrapper templateWrapper) {
        OapiWrapper oapiWrapperForTechUser = templateWrapper;
        OapiWrapper oapiWrapperForAuthUser = templateWrapper;
        //.....
    }
    //.....
}
```
Т.е. метод просто скопирован один-в-один из другого класса. Проблема получилась из-за того, что метод оказался в классе, где он впервые потребовался. 
А когда выяснилось, что в совершенно другом классе потребовался вызов полностью аналогичного кода,  разработчик (ладно хоть не я) вместо его вынесения в отдельную сущность или же поиск имеющегося подходящего класса (я навскидку правда не нашел) просто скопировал метод as is.

#### 2.4. Класс хранит данные, которые загоняются в него в множестве разных мест в программе. 
В продукте есть класс RunInfo. Данный класс отвечает не только собственно за свою внутреннюю модель/правила, но и по сути учавствует в управлении бизнес-процессом в системе.
В итоге в данный класс вносятся изменения/дополнения из 10 классов.

Возможно, для данного примера плохого проектирования подходят классы из первого пункта, когда при нарушении SRP возникают большие классы, требующие для разных своих "частей" соответственно разных данных, логично разнесенных по разным местам программы.

#### 2.5. Класс зависит от деталей реализации других классов. 
Для данного пункта в нашем коде много примеров (которые в том числе я уже приводил в некоторых прошлых заданиях) - это цепочки вызовов геттеров. 
Фактически мы получаем зависимость то внутренней структуры других классов.
```java
rti.getRunInfo().getRun().getRequest().getNaviDate().toInstant();
```

Еще один из частых примеров в коде - прямой доступ к публичным полям классов. Это часто встречается наверное из-за спешки (или лени), потому что уж совсем неправильное поведение.

#### 2.6. Приведение типов вниз по иерархии (родительские классы приводятся к дочерним). 
Это пример нарушения принципа подстановки Лисков и/или признак неправильно выстроенной иерархии классов. 
В рабочем коде не нашел (уверенно)-подходящих примеров.
Как пример вспомнил такой - если в коде требуется явное приведение типа для выолнения конкретного метода, классы спроектированы плохо.
Из классики наверное
```java
Animal animal = getAnimal();
if (animal instanceof Dog) {
        ((Dog) animal).Bark();
}

// а в правильном проектировании/реализации просто
Animal animal = getAnimal();
animal.makeSound();
```
#### 2.7. Когда создаётся класс-наследник для какого-то класса, приходится создавать классы-наследники и для некоторых других классов.
Возникает когда разработчик пытается сущности из физического мира перенести as is "в лоб" в программу или если на этапе проектирования или в процессе расширения системы не выделить общий класс (или тут правильно сказать про доменную модель?) можно легко получить параллельные иерархии наследования.
В коде с проблемами параллельных иерархий у нас есть работа со статистикой (собственно недавно мы эту проблему обсуждали в команде).
Чтобы добавить новую метрику потребуется пять новых типов в пяти пакетах и пяти независимых иерархиях:
- NewMetricStatistic extends AbstractStatistic
- NewMetricStatsProcessor implements MonitoringProcessor
- NewMetricStatisticProcessor extends AbstractJmxProcessor
- NewMetricStats extends CalculableMetric
- NewMetricStatsMBean extends JmxBean

Собственно это почти дословная копия с рабочего чата по проблеме.

#### 2.8. Дочерние классы не используют методы и атрибуты родительских классов, или переопределяют родительские методы. 
Возникает при наследовании для переиспользования кода, когда разработчику нужно всего несколько методов из родительского класса и он вместо композиции делает наследование.
Еще возможно при изменении требований к дочерним классам, когда вследствие развития системы поведение дочерних классов сильно изменилось, но базовый класс трогать нельзя, тогда в наследниках переопределяют или зануляют методы родителя.

Кстати, хороший пример для данного пункта - это пример (кажется первый же) про уток, метод Fly и далее интерфейс FlyBehavior из Design Patterns Фримена.

#### 3.1. Одна модификация требует внесения изменений в несколько классов.
Проблему получаем при жесткой связанности классов из-за сильных зависимостей от внутренних структур данных или типов других классов.
Размазанная по коду (по разным классам) логика. Собственно уже не раз рассмотренное выше нарушение SRP.
Вот один из примеров буквально двумя пунктами выше - это параллельные иерархии. Добавление одной метрики приведет к добавлению 5 новых классов.
Еще пример: есть сущность RequestRunState. Появление нового статуса приведет к изменению 9 файлов (блоки switch и if-else)

#### 3.2. Использование сложных паттернов проектирования
Оверинжиниринг. Преждевременная оптимизация "на всякий случай" для будущего, которое вероятнее всего не наступит (в тг относительно недавно у Вас несколько материалов на эту тему было).
У нас в продукте есть вот такое:
```java
// Абстрактная фабрика ДАО
public abstract class DaoFactory {

    public enum AvailableDao {
        OAPI
    }

    // Перечисление доступных ДАО
    public static final int OAPI = 1;

    // Метод для создания каждого из доступных ДАО
    // Конкретные фабрики должны реализовывать эти методы
    public abstract SubscriberDao getSubscriberDao();

    public static DaoFactory getDaoFactory(AvailableDao whichFactory) {
        switch (whichFactory) {
            case OAPI:
                return new OapiDaoFactory();
            default:
                return null;
        }
    }
}
```
Одно значение в enum, ни одного вызова getDaoFactory(), везде (в 4 местах) вызов напрямую new OapiDaoFactory().
Т.е. использование здесь паттерна "Фабрика" явно излишне. Задел был явно на будущее, которое не наступило.
